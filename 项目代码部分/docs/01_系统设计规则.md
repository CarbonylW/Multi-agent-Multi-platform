## 1. 架构设计规则

### 1.1 三层架构 + 侧边状态管理器

```
                        ┌─────────────────────────┐
                        │   L1 全局统筹Agent     │
                        │  (混合决策架构)        │
                        └───────────┬─────────────┘
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        │                           │                           │
        │              ┌────────────▼─────────────┐             │
        │              │   🔄 状态管理器          │             │
        │              └────────────┬────────────┘             │
        │                           │                              │
        └───────────────────────────┼───────────────────────────┘
                                    │
                        ┌───────────▼─────────────┐
                        │  L2 设备类型Agent层      │
                        └───────────┬─────────────┘
                                    │
                        ┌───────────▼─────────────┐
                        │   L3 实际物理设备层      │
                        └─────────────────────────┘
```

### 1.2 通信规则

- ✅ L1 ↔ 状态管理器 双向通信
- ✅ L2 ↔ 状态管理器 双向通信
- ✅ L2 ↔ L3 双向通信（直接协议报文）
- ❌ L1 不能直接控制 L3 设备
- ❌ L2 之间不能直接通信
- ❌ 设备状态不再双上报，统一上报给状态管理器

## 2. 状态管理规则

### 2.1 推拉模式

**推送（Push）**：仅在异常时推送
- 设备状态异常（故障、离线、通信中断等）
- 状态管理器主动推送给 L1 和 L2
- 推送内容：异常设备ID、异常类型、异常时间、当前状态

**拉取（Pull）**：需要时才拉取
- **L1 拉取时机**：
  - 任务调度时，查看设备可用性
  - 决策需要全局态势时
  - 收到异常推送后
- **L2 拉取时机**：
  - 接收 L1 任务规划后
  - 执行任务需要了解设备状态时
  - 收到异常推送后

**平时状态**：
- 状态只在状态管理器中流转
- L1/L2 不与设备维持长连接
- L1/L2 不实时获取所有设备状态

### 2.2 状态一致性解决方案

采用 **"状态版本号 + 乐观锁 + 冲突仲裁"** 机制

#### 2.2.1 状态版本号

```
设备上报状态时：
    带上自增的版本号（每次上报 +1）
    ↓
状态管理器存储：
    保存：当前状态 + 最新版本号 + 时间戳
```

#### 2.2.2 乐观锁机制

```
L1/L2 读取状态时：
    获取：状态数据 + 版本号 + 时间戳
    ↓
L1/L2 基于此状态做决策后：
    提交决策时，必须带上读取时的版本号
    ↓
状态管理器校验：
    IF 提交的版本号 == 当前最新版本号：
        ✓ 执行决策
    ELSE：
        ✗ 拒绝执行，提示"状态已过期，请重新获取"
```

#### 2.2.3 补充保护机制

**1. 时间窗口保护**
- 决策从读取状态到执行，超过一定时间（默认 5 秒），即使版本号一致也需要重新确认
- 可配置的时间窗口：紧急任务 3 秒，普通任务 10 秒

**2. 关键状态加锁**
- 设备执行任务时，对该设备加"操作锁"
- 锁的持有者可以操作，其他人不能同时发送冲突指令
- 任务完成或异常时自动释放锁

**3. 状态差异容忍度**
- 位置误差 < 5 米 → 认为一致
- 速度误差 < 1 m/s → 认为一致
- 姿态误差 < 10 度 → 认为一致
- 超过阈值触发重新获取状态

**4. 决策预校验**
- L1/L2 下发决策前，先问状态管理器："这个决策还适用吗？"
- 状态管理器快速检查状态是否发生重大变化
- 预校验通过后再执行正式提交

## 3. Agent自主权边界规则

### 3.1 L2 规划与审阅流程

```
L2 接收 L1 任务规划
    ↓
L2 自主规划航线/动作
    ↓
L2 提交规划给 L1 审阅
    ↓
L1 审阅（可以批准、修改或拒绝）
    ↓
L2 执行（或根据 L1 反馈调整）
```

### 3.2 避障等紧急情况处理

**规则**：L2 可以自己改，但必须留档报备

```
L2 检测到紧急情况（如前方有障碍）
    ↓
L2 立即自主修改航线/动作（无需等待 L1 批准）
    ↓
同时执行以下操作：
    1. 立即执行新航线/动作
    2. 记录变更日志（时间、原因、变更内容）
    3. 更新状态管理器中的设备状态
    4. 向 L1 报备（附上变更原因和日志）
    ↓
L1 收到报备后记录，但不强制干涉（除非发现问题）
```

### 3.3 报备内容要求

报备必须包含：
- 变更时间戳
- 变更触发原因（如"检测到障碍物"、"航线冲突"等）
- 原计划 vs 新计划的对比
- 设备当前状态
- 变更日志

## 4. 决策融合规则

### 4.1 核心原则

- ❌ **不允许硬编码规则**来选择用 LLM 还是传统算法
- ✅ **优先让 LLM 判断**，由 LLM 决定如何处理
- ✅ **LLM 先想，传统算法校验**
- ✅ **必须有兜底机制**

### 4.2 决策流程

```
输入：任务 + 态势信息
    ↓
步骤1：LLM 理解问题，生成决策方案
    ↓
步骤2：传统算法对 LLM 方案进行校验
    ├─ 可行性检查（物理可达、资源充足等）
    ├─ 安全性检查（无冲突、无风险等）
    └─ 最优性检查（是否有更优解）
    ↓
步骤3：根据校验结果处理
    ├─ ✓ 校验通过 → 执行 LLM 方案
    ├─ ⚠️ 校验有小问题 → 传统算法微调后执行
    └─ ✗ 校验不通过 → 触发兜底机制
    ↓
步骤4：兜底机制（如 LLM 方案完全不可行）
    └─ 传统算法生成安全保底方案
```

### 4.3 兜底机制

兜底触发条件：
- LLM 返回格式错误
- LLM 方案被传统算法判定为不可行
- LLM 调用超时或失败
- LLM 方案存在明显安全风险

兜底策略：
- 使用传统规划算法生成安全保底方案
- 记录兜底触发原因和 LLM 原始输出
- 事后分析，优化 Prompt 或流程

## 5. 冲突检测规则

### 5.1 两级冲突检测架构

```
L2 规划航线/动作
    ↓
步骤1：L2 初步冲突检测（自己管的设备之间）
    ├─ 检测：同一类型设备之间的冲突
    ├─ 消解：自己能解决的自己解决
    └─ 报备：解决后报备 L1（留档）
    ↓
步骤2：L2 提交规划给 L1
    ↓
步骤3：L1 全局冲突检测（不同类型设备之间）
    ├─ 检测：无人机、无人艇、潜航器之间的跨域冲突
    ├─ 仲裁：发现冲突时进行全局仲裁
    └─ 决策：批准、修改或拒绝 L2 的规划
```

### 5.2 突发情况处理

**规则**：L2 自己处理，然后报备，L1 有最高打断权

```
L2 执行中发现突发冲突
    ↓
L2 立即自主处理（无需等待 L1）
    ↓
同时：
    1. 立即执行消解动作
    2. 记录冲突和处理日志
    3. 更新状态管理器
    4. 向 L1 报备
    ↓
L1 收到报备后：
    1. 验证 L2 的处理是否正确
    2. ✓ 没问题 → 记录，不干涉
    3. ✗ 发现问题 → 立即向 L2 下发终止/修正指令
       （注意：L1 仍不直接控制设备，只命令 L2）
```

### 5.3 L1 的最高决策权

L1 可以随时：
- 要求 L2 暂停当前动作
- 要求 L2 修改规划
- 命令 L2 终止任务
- 接管决策权（但仍通过 L2 执行）

但 L1 **不能**：
- 直接向设备发送指令
- 绕过 L2 控制设备
